## خريطة الملكية والمصادر

- **حالة المحتوى/التقويم:** `apps/web/src/app/(app)/app/content/content-client.tsx`؛ يملك React حالة المبدل والتاريخ وبيانات البطاقات. لا تُنسخ البيانات ولا يتغير مصدرها.
- **المسار العلوي والـ rail:** `apps/web/src/components/shell/shell-chrome.tsx` مع الأنماط في `apps/web/src/styles/shell.css` و`apps/web/src/app/globals.css`.
- **بطاقات/خلايا التقويم ولوحة الفلترة:** `apps/web/src/components/content/planable-views.tsx` و`apps/web/src/styles/content-views.css` وطبقة التوافق المتأخرة `apps/web/src/styles/planable-org.css`.
- **قواعد العرض المتراكمة:** `apps/web/src/styles/stage3.css` ثم تجاوزات الهاتف والـ globals؛ ترتيب الاستيراد في `globals.css` جزء من التشخيص، ويجب تعديل مالك القاعدة أو إضافة قاعدة موضعية واحدة واضحة بدل تكرار selectors متضاربة.
- **التحقق:** اختبارات Vitest الموجودة للمحتوى/الهيدر، واختبار Playwright محدود على صفحة المحتوى إذا أمكن تشغيل مجموعة E2E على قاعدة `oma_ai_e2e` فقط.

## التصميم

- **نوع الشاشة:** Content Calendar — تقويم إنتاج/نشر قائم على شبكة الأيام.
- **نمط Planable المرجعي:** شريط أدوات تقويم واضح، مسار علوي مضغوط، قوائم منبثقة مرتبطة بعنصرها، وخلايا يوم قابلة للتمرير بعد عرض المحتوى المرئي.
- **تكييف OMA:** تبقى سكة التنقل الجانبية بعرضها المعتمد، ويأخذ عمود المحتوى المساحة المتبقية. قوائم التقويم لا تستخدم إزاحة ثابتة مشتقة من عرض rail؛ الهيدر لا يلف، بل يختصر الوسوم الثانوية عند الحاجة. تحافظ الخلية على بطاقات المحتوى ومؤشرات حالتها كما هي.
- **المظهر:** الحفاظ على Canvas/Surface والتباعد والتباين الحالي وفق Planable tokens؛ لا إضافة ألوان أو مكونات أو حركة جديدة.
- **التفاعل وإتاحة الوصول:** يبقى مبدل العرض والـ week/month controls قابلين للتشغيل بلوحة المفاتيح؛ التموضع يراعي scroll/resize وحالة rail والـ RTL؛ لا يُخفى محتوى حالة أو إجراء أساسي.

## هيكل المشروع المتأثر

- `apps/web/src/app/(app)/app/content/`: مالك صفحة المحتوى وتفاعلات التقويم.
- `apps/web/src/components/shell/`: المسار العلوي وحالة rail ومساحة العرض.
- `apps/web/src/components/content/`: بطاقات التقويم المشتركة.
- `apps/web/src/styles/` و`apps/web/src/app/globals.css`: قواعد shell والتقويم واللوحة الجانبية وترتيب cascade.
- `tests/unit/` و`tests/e2e/`: إثبات عقود التخطيط دون تعديل API أو إعدادات البيانات.

## النهج التقني

1. حصر قواعد `.oma-cal-toolbar`, `.oma-view-menu__list--path`, breadcrumb, `.oma-cal-grid[data-span]`, و`.oma-content-filter-eyebrow` في كل ملفات CSS المحملة، واستخدام اختبار بصري/DOM لتأكيد القاعدة الرابحة.
2. جعل شريط التقويم داخل تدفق عمود المحتوى مع `min-width: 0` وflex-wrap، وإلغاء sticky بدل رفع طبقته فوق التنقل.
3. وضع قائمة مبدل العرض بمحاذاة `#oma-content-view-slot` من أبعاد العنصر الحالية (LTR/RTL)، مع fallback إلى زر التبديل حين يخفي الهاتف المسار؛ إعادة الحساب عبر resize/scroll/ResizeObserver/MutationObserver، وتقييدها داخل viewport بطبقة أدنى من rail.
4. ضغط مسار breadcrumb في سطر واحد؛ إعطاء منطقة المسار قابلية الانكماش وإتاحة ellipsis للنصوص الثانوية، مع تثبيت مساحة أزرار الإجراءات.
5. تعيين صفوف الشهر إلى حد أدنى 260px (220px compact) وخلايا الأسبوع إلى 220px (200px compact) بما يستوعب بطاقتين، مع استمرار سلوك العناصر الزائدة والتمرير داخل الخلية.
6. ضبط الحشوة الأفقية للوحة الفرز/الفلترة إلى 16px وإلغاء الهوامش الخارجية التي تجعل صف التحكم أعرض من جسم اللوحة.
7. تعديل أضيق مواصفة responsive ذات صلة بعد التحقق، وتحديث المهام بنتائج التنفيذ. لا تعديل على `/app/schedule` إلا إذا أثبت الفحص أن القواعد المشتركة تتسبب بتراجع.

## فحص الدستور

- لا يتغير مالك البيانات أو التخزين أو واجهة API أو حد tenant.
- لا تتغير حالات المحتوى أو النقلات الخادمية؛ الواجهة تظل عرضًا لنفس مصدر الحقيقة.
- يدعم التعديل EN/AR وLTR/RTL، keyboard، والقياسات المطلوبة.
- يُستخدم Planable مرجعًا بصريًا وحيدًا، مع بقاء نصوص ومكونات OMA أصلية.

## حالة التنفيذ والتحقق

- نُفذت تغييرات العرض في `content-client.tsx` و`globals.css`، وأضيف اختبار وحدة لعقود التموضع والـ RTL والارتفاعات والـ gutters.
- نجحت اختبارات Vitest ذات الصلة (16/16)، و`pnpm --filter @oma/web typecheck`، وPrettier، و`git diff --check`.
- `pnpm typecheck` الشامل متعثر في `@oma/db` بسبب عدم توفر مراجع/تصديرات Prisma في التوليد الموجود؛ لم يظهر فشل في TypeScript الخاص بتطبيق الويب.
- مراجعة المقاسات بصريًا وPlaywright ما زالت مفتوحة؛ متغيرا قاعدة E2E غير مضبوطين ولم يمكن التحقق من خدمة PostgreSQL في البيئة، لذا لا يُدّعى اجتياز القبول المرئي.
